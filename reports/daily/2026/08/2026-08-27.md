# Termination Leaves Residue / 终止之后仍有残留状态

## 0｜Executive Judgment / 核心判断

W35 has progressed from live trust to resource denial and then to explicit Agent-runtime stop controls

Today adds the next lifecycle distinction:

> **Stopping execution does not erase state that already exists**

Current public product semantics separate at least four actions:

```text
CANCEL OPERATION
≠ STOP SESSION / COMPUTE
≠ DELETE RETAINED STATE
≠ REVERT / COMPENSATE DURABLE EFFECT
```

OpenAI Realtime exposes operation-level cancellation: an in-progress response can be cancelled while the session itself remains intact

GitHub Agent-session stop ends continued Agent work / the associated Actions run, while already-pushed commits remain

Microsoft Foundry hosted-session stop terminates running compute while preserving persistent filesystem state for later resume; deleting the sandbox/session resources is a separate lifecycle action

GitHub also models rollback of already-merged code as a separate new revert pull request rather than as part of stopping the original work

These mechanisms are product-specific and do not form one portable Agent incident protocol

But they support a durable structural judgment:

> **Termination and remediation are separate lifecycle phases**

## 2｜Cancellation is not one state / 取消不是单一状态

### Operation cancellation

OpenAI Realtime `response.cancel` cancels an in-progress response

The response reaches a cancelled terminal status, but the surrounding session remains

This proves a narrow but important semantic distinction:

> **cancel current generation ≠ terminate session**

### Session / compute stop

GitHub and Microsoft Foundry expose broader session/runtime stop controls

Those controls halt future execution at their platform boundary but preserve some prior state

Therefore:

> **stop ≠ erase**

## 3｜Durable effects survive stop / 持久副作用会跨越停止边界

GitHub documents that commits already pushed by the coding Agent remain after session stop

For a merged change, GitHub's revert workflow creates a **new pull request** that reverts the original merge commit

This is strong evidence that remediation is a new governed action rather than an automatic consequence of runtime termination

The same logic applies more broadly to non-code systems:

- a sent message may require correction or follow-up
- a ticket mutation may require another state transition
- a cloud-resource change may require compensating infrastructure action
- a dataset publication may require supersession / withdrawal rather than session cancellation

These are observatory analogies, not claims that GitHub defines those non-code semantics

## 4｜Persistent local state survives stop / 本地持久状态也可能保留

Microsoft Foundry hosted sessions separate STOPPED state from deletion

Stopping terminates active compute but preserves the persistent filesystem volume for possible resume

This means incident handling must distinguish:

```text
COMPUTE STATE
from
PERSISTENT SESSION STATE
```

A later resume should therefore not be treated as semantically equivalent to a clean new execution

The remaining question is whether resume is systematically conditioned on fresh identity, policy, delegation and risk evaluation

## 5｜H10 — Termination and remediation become separate lifecycle phases

**NEW / STRONG CROSS-PRODUCT STRUCTURAL SIGNAL**

The evidence now spans operation cancellation, session stop, retained state and explicit rollback/remediation mechanisms

**Falsifier:** mature autonomous systems consistently make stop/cancel transactional across all durable internal and external effects, eliminating any independent reconciliation or compensation phase

## 8｜Remaining Missing Bridge / 仍缺失的桥

Public evidence still does not establish a portable end-to-end incident object binding:

```text
incident_id
```

This is an observatory analytical model, not a published standard

## 9｜Implications for Agent architecture / 对 Agent 架构的意义

The lifecycle is no longer well represented by a binary `running / stopped` flag

A more realistic control plane needs separate state for:

- operation status
- session/runtime status
- retained local state
- durable output status
- external authority / credentials
- remediation status
- resume eligibility

This strengthens W35's original thesis: live trust is a distributed state-synchronization problem
