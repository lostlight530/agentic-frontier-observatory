## 0｜Executive Judgment / 核心判断

W34 proved that governance can enter real execution paths: session evidence can be audited, source changes can carry provenance, build artifacts can be attested, and admission policy can allow or reject runtime entry

W35 opens with the harder question left unresolved on Sunday:

> **What happens after admission when trust changes?**

GitHub artifact-attestation enforcement is an admission-time mechanism: a Kubernetes admission controller can verify provenance before a workload is admitted. GitHub also supports deleting attestations, which can make later verification fail. Neither mechanism by itself proves that an already-running workload will automatically terminate

NIST Zero Trust deployment guidance provides an important architectural contrast. Its runtime model explicitly includes continuous access evaluation and a policy decision path that can continue, limit, or revoke an active session when subject, resource, environment, or telemetry state changes

SPIFFE adds a second runtime primitive: workload identities use short-lived, automatically rotated credentials and frequently refreshed trust bundles

Taken together, these sources do **not** establish a universal Agent revocation standard. They do establish a stronger W35 research frame:

```text
ADMISSION-TIME TRUST
Artifact provenance
→ policy evaluation
→ admit / reject

RUNTIME TRUST
workload identity
→ session policy
→ telemetry / environment state
→ continuous re-evaluation
→ continue / limit / revoke
```

Today’s core judgment is therefore:

> **Trust must remain live after admission**

A revocation signal matters only if it can reach an enforcement point capable of changing the real running state

## 2｜Admission and runtime are different boundaries / 准入与运行时是不同边界

GitHub’s Sigstore-based Kubernetes admission flow can stop an artifact from entering a cluster when provenance policy fails

That is a durable admission boundary

NIST’s Zero Trust architecture separately models ongoing access after a session has started. A policy engine can continuously reconsider access and direct policy enforcement points to limit or disconnect the session

**ANALYSIS** — W35 must treat these as distinct control phases:

```text
PRE-RUNTIME
verify → admit

IN-RUNTIME
observe → re-evaluate → continue / limit / revoke
```

## 3｜Artifact trust and workload identity are different clocks / 构建信任与工作负载身份是不同时间尺度

Artifact attestations answer questions about where and how an artifact was built

SPIFFE workload identity answers which running workload is presenting an identity at that moment. Its X.509-SVIDs are deliberately short-lived and automatically rotated

These are complementary, not interchangeable

```text
ARTIFACT TRUST
source / build / digest / attestation

WORKLOAD TRUST
identity / credential / trust bundle / runtime session
```

A secure runtime may need both, plus delegated human or Agent authority

## 4｜Revocation is a propagation problem / 撤销本质上是传播问题

Deleting an attestation changes future verification state

Rotating or expiring workload credentials changes identity state

Changing user or Agent authorization changes authority state

Changing runtime telemetry changes risk state

The system challenge is whether these changes converge on the same effective enforcement boundary quickly enough

> **Revocation signal ≠ revocation propagation ≠ runtime termination**

## 5｜W35 Opening Hypotheses / W35 开周假设

### H1 — Runtime trust requires continuous re-evaluation

Admission-time verification alone is insufficient for long-lived autonomous execution

**Falsifier:** production Agent systems can remain safely governed for long-lived execution with only one-time admission decisions and no equivalent ongoing policy evaluation

### H2 — Revocation requires an explicit enforcement point

A lifecycle signal only matters operationally if a policy enforcement point can limit, disconnect, revoke, or replace the affected session/workload

**Falsifier:** revocation can reliably change runtime state without an identifiable enforcement mechanism

### H3 — Artifact trust and workload identity must remain distinct but correlated

Build provenance and runtime identity solve different problems and should not be collapsed into one overloaded credential

**Falsifier:** one interoperable primitive safely captures both build provenance and live workload identity without losing semantics

### H4 — Short-lived identity reduces exposure but does not replace policy revocation

Credential rotation bounds identity exposure but does not automatically revoke artifact trust, delegated authority, or business permission

**Falsifier:** short-lived workload identity alone proves sufficient for all relevant runtime trust changes

### H5 — Exception paths become lifecycle objects

Break-glass and policy exceptions must carry owner, scope, expiry, reason, and audit evidence rather than becoming permanent bypasses

**Falsifier:** mature systems can safely rely on unstructured exceptions without increasing governance blind spots

### H6 — Non-code Agent outputs need an equivalent lifecycle

Documents, tickets, CRM writes, infrastructure changes, datasets, and other durable outputs require publication/admission/revocation semantics comparable to code artifacts

**Falsifier:** non-code Agent outputs remain safely governed without durable provenance or lifecycle boundaries

### H7 — End-to-end correlation becomes incident infrastructure

Incident response will require a trace from Agent definition → session → delegated identity → artifact/output → runtime/workspace state

**Falsifier:** incidents can be reconstructed reliably without cross-layer correlation

## 6｜Evidence boundary / 证据边界

- NIST Zero Trust is general runtime access-control guidance, **not an Agent-specific standard**
- SPIFFE is workload identity infrastructure, **not Agent authorization or provenance**
- GitHub attestation admission is build-provenance enforcement, **not proof of application safety**
- continuous session evaluation in one architecture does not prove all Agent platforms implement it
- credential expiry does not equal policy revocation propagation
