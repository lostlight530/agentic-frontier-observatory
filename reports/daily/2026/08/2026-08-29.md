## 0｜Executive Judgment / 核心判断

W35 has progressed from live trust to denial, stop, reconciliation and a new recovery-task boundary

Saturday asks the next question:

> **If recovery creates a new execution identity, what authority does that new task actually carry?**

A2A provides unusually direct protocol evidence here

- every incoming request must be authenticated
- the server authorizes requests using the authenticated identity and its own policies
- task operations must remain scoped to the caller's authorization boundary
- in-task authorization can transition a Task into `TASK_STATE_AUTH_REQUIRED`
- a new Task can preserve `contextId` continuity without reusing the terminal Task identity

This supports a stronger W35 refinement:

> **Recovery re-entry is an authorization boundary**

But the claim must remain precise

> **Fresh authorization check ≠ fresh human approval ≠ fresh credential**

A server may accept an existing valid credential and still perform a new authorization decision for the successor request

## 3｜A2A Evidence / A2A 证据

### Every request is a security boundary

The A2A server authenticates incoming requests according to its declared security requirements and performs authorization based on authenticated identity and implementation-specific policy

Task access operations such as list/get/cancel/subscribe must respect the caller's authorized access boundary

### Context does not carry authority

`contextId` logically groups related Tasks and Messages

It can preserve semantic continuity across a new Task

But authorization is still checked at the request/resource boundary

Therefore:

```text
same context
≠ same task
≠ same authorization result
```

### AUTH_REQUIRED makes authority state explicit inside work

A2A permits an active Task to enter `TASK_STATE_AUTH_REQUIRED` when additional authorization is needed for an action

This shows that authority can become insufficient during task execution rather than being treated as a permanent property of the context

A critical boundary from the specification is equally important:

> entering `AUTH_REQUIRED` is not itself proof that later action is authorized

Authorization still has to be evaluated for the relevant operation

## 4｜MCP Evidence / MCP 证据

MCP Tasks remains useful as the contrasting execution model

Its cooperative, eventually consistent cancellation means the old Task may not stop exactly when cancellation is acknowledged

Therefore a recovery controller cannot safely infer the successor Task's authority merely from a cancellation ACK or from the old Task's last visible state

```text
cancel requested
≠ cancel observed
≠ execution physically stopped
≠ successor authority established
```

## 7｜Cross-System Analysis / 跨系统分析

The security and execution planes remain distinct

```text
TASK IDENTITY
≠ PRINCIPAL IDENTITY
≠ CREDENTIAL
≠ AUTHORIZATION DECISION
≠ USER INTENT
```

A2A contributes a protocol-level request / Task boundary

MCP Tasks contributes durable asynchronous execution and cooperative cancellation semantics

Vendor-local runtime controls contribute session stop, retained-state and remediation behavior

These are complementary layers, not one unified cross-protocol recovery standard

## 9｜Uncertainties and Watchlist / 不确定与观察点
