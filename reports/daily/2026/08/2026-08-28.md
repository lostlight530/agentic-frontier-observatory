# Recovery Gets a New Task Boundary / 恢复获得新的任务边界
## Global AI Daily Research Report / 全球人工智能每日研究报告
### 2026-08-28

**Observation cut-off / 观察截止：2026-08-28 07:41 CST**

## 0｜Executive Judgment / 核心判断

W35 has moved through four increasingly concrete runtime layers:

```text
24 Aug  continuous runtime trust
25 Aug  trust change → relying-resource denial
26 Aug  explicit runtime stop
27 Aug  stop → residual-state inventory → remediation
```

Today adds a fifth layer:

> **Recovery after a terminal task state requires a new execution boundary, not an invisible resurrection of the old task**

Two open-protocol families now expose the distinction clearly enough to matter

### A2A

A2A models work as stateful `Task` objects with unique task IDs, current state, artifacts and history

Its current specification treats `completed`, `failed`, `canceled` and `rejected` as terminal task states and states that a task that reaches a terminal state cannot be restarted

At the same time, `contextId` can group multiple related tasks and messages

This creates a useful separation:

```text
TASK CONTINUITY
≠
CONTEXT CONTINUITY
```

A failed or canceled task can remain historical evidence while later work continues under a new task identity inside the same broader context

### MCP Tasks

The 2026-07-28 MCP release moved long-running work into the `io.modelcontextprotocol/tasks` extension

The extension gives asynchronous work a server-generated `taskId` and lifecycle methods such as `tasks/get`, `tasks/update` and `tasks/cancel`

The current Tasks extension draft is especially important for W35 because cancellation is cooperative and eventually consistent

A cancellation request can be acknowledged while observable task state has not yet changed, and underlying work may race to another terminal state

This means:

> **Cancellation intent ≠ proven physical termination**

Together, A2A and MCP strengthen a new runtime-governance principle:

```text
INCIDENT / CANCELLATION
→ TERMINAL TASK RECORD
→ RESIDUAL-EFFECT RECONCILIATION
→ NEW TASK / EXECUTION IDENTITY
→ CONTEXTUAL CONTINUITY
→ FRESH AUTHORIZATION / POLICY
→ RECOVERY WORK
```

The key boundary is therefore:

> **Context continuity ≠ task restart ≠ authority continuity**

No source reviewed today establishes a universal recovery protocol, a portable compensating-transaction object, or automatic transfer of prior delegated authority into a new recovery task

## 1｜Why this is a real W35 advance

Yesterday established that termination and remediation are separate phases

But the weekly model still had an ambiguous `resume`

Today makes that ambiguity more precise

A runtime can preserve context, artifacts or state while the exact task that failed or was cancelled remains terminal

Recovery therefore needs to answer at least three separate questions:

1. **What historical execution object is now closed?**
2. **What new execution object performs cleanup or recovery?**
3. **Which identity / delegation / policy evidence authorizes that new object?**

That is stricter than simply calling `resume()`

## 2｜A2A — terminal task, continuing context

A2A defines a task as the stateful unit of work

A task carries:

- task ID
- context ID
- task status
- output artifacts
- interaction history
- extension metadata

The lifecycle includes terminal states such as completed, failed, canceled and rejected

The current specification says terminal tasks cannot be restarted

But one `contextId` can logically compose many related tasks and messages

This produces a durable architectural distinction:

```text
old_task_id = historical execution evidence
new_task_id = new execution attempt / recovery work
context_id = continuity across related work
```

### Boundary

A2A does not thereby define:

- compensation semantics
- rollback semantics
- trust re-evaluation policy
- credential refresh rules
- incident ownership
- transfer of authority between the old and new task

So:

> **New task identity ≠ authorized recovery**

## 3｜MCP Tasks — cancellation is a coordination signal

The MCP 2026-07-28 specification formally includes an extensions framework and moves long-running Tasks into that model

The Tasks extension represents durable asynchronous work through a task handle and lifecycle operations

The current extension text states that tasks are durable state machines and assigns every task a stable server-generated task ID

The draft cancellation semantics are even more instructive:

- cancellation is cooperative
- the server decides whether and when to honor it
- acknowledgement does not necessarily mean task state has already transitioned
- race conditions may allow work to finish before cancellation takes effect

This sharpens yesterday's rule

```text
cancel requested
≠
cancel observed
≠
execution physically stopped
≠
durable effects reconciled
```

### Boundary

The detailed Tasks extension page currently carries **Draft** status

It must not be mislabeled as a finalized universal incident-recovery standard

The final MCP 2026-07-28 release establishes Tasks as an official extension family, while the extension specification continues to evolve on its own lifecycle

## 4｜The recovery identity problem

Once a task is terminal, blindly reusing the same execution identity creates audit ambiguity

A cleaner incident model is:

```text
incident_id
→ original_task_id
→ terminal_state
→ residual_effect_inventory
→ remediation_plan
→ recovery_task_id
→ recovery_authority_evidence
→ remediation_actions
→ completion_evidence
→ follow-up validation
```

This is an observatory analytical model, not an official schema

The important change from yesterday is that `recovery_task_id` now has protocol-level precedent as a distinct execution object rather than only an abstract workflow step

## 5｜W35 Hypothesis Update

### H1 — Runtime trust requires continuous re-evaluation

**STRONGLY STRENGTHENED**

A new recovery task should not inherit stale trust merely because it shares context with the failed task

### H2 — Revocation requires explicit enforcement points

**STRONGLY STRENGTHENED / REFINED**

Cancellation, terminal task state and later recovery-task creation are separate control surfaces

### H3 — Artifact trust and workload identity remain distinct but correlated

**SUPPORTED**

Artifacts/history can survive a terminal task and become inputs to a new execution object without becoming its authority

### H4 — Short-lived identity does not replace policy revocation

**STRENGTHENED**

Task identity and authorization remain distinct

### H5 — Exception paths become lifecycle objects

**OPEN / stronger pressure**

Recovery tasks are a natural place to require explicit exception ownership, scope and expiry, but no portable model was found today

### H6 — Non-code Agent outputs need equivalent lifecycle boundaries

**STRENGTHENED PRESSURE**

A new recovery task may need to supersede or compensate documents, tickets, CRM mutations or infrastructure changes created by the original task

### H7 — End-to-end correlation becomes incident infrastructure

**STRONGLY STRENGTHENED**

Correlation now needs original task ID, terminal state, recovery task ID and shared context / incident ID

### H8 — Relying-resource participation matters to revocation

**STRONG IMPLEMENTATION SIGNAL / unchanged**

### H9 — Explicit Agent-runtime termination is a first-class control primitive

**STRONGLY STRENGTHENED**

Open protocols now add task-level lifecycle semantics on top of product-local stop controls

### H10 — Termination and remediation are separate lifecycle phases

**STRONGLY STRENGTHENED**

A terminal task can remain an immutable historical boundary while a different task performs reconciliation

### H11 — Recovery requires a new execution identity boundary

**NEW / STRONG OPEN-PROTOCOL STRUCTURAL SIGNAL**

A2A terminal tasks cannot be restarted while context can continue across multiple tasks; MCP Tasks gives long-running work stable task identity and cooperative cancellation semantics

**Falsifier:** mature interoperable Agent systems consistently recover failed/cancelled work by transparently reactivating the same terminal execution object with unchanged authority, without creating a new auditable execution identity

## 6｜Durable rules added today

```text
context continuity ≠ task restart
terminal task ≠ deleted history
cancellation intent ≠ proven termination
task ID ≠ authorization identity
new task ≠ inherited authority
recovery task ≠ automatic compensation
shared context ≠ shared credential
historical artifacts ≠ current execution permission
```
