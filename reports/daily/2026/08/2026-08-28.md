# Recovery Gets a New Task Boundary / 恢复获得新的任务边界
## Global AI Daily Research Report / 全球人工智能每日研究报告
### 2026-08-28

**Observation cut-off / 观察截止：2026-08-28 07:41 CST**

## 0｜Executive Judgment / 核心判断

W35 has moved through five increasingly concrete runtime layers:

```text
24 Aug  continuous runtime trust
25 Aug  trust change → relying-resource denial
26 Aug  explicit runtime stop
27 Aug  stop → residual-state reconciliation
28 Aug  terminal task → new recovery-task identity
```

28 August adds a new execution-identity boundary:

> **Recovery after a terminal task state requires a new execution boundary, not an invisible resurrection of the old task**

A2A provides the clearest protocol evidence:

- a `Task` is a stateful work unit with task ID, context ID, status, artifacts and history
- completed, failed, canceled and rejected states are terminal
- a terminal Task cannot be restarted
- one `contextId` can still group multiple related Tasks and Messages

MCP Tasks independently strengthens the execution-state side:

- long-running work receives a stable server-generated `taskId`
- task lifecycle methods include `tasks/get`, `tasks/update` and `tasks/cancel`
- cancellation is cooperative and can race with underlying execution

Together they support:

```text
TERMINAL TASK RECORD
→ KEEP HISTORICAL EXECUTION EVIDENCE
→ RECONCILE RESIDUAL EFFECTS
→ NEW RECOVERY TASK
→ CONTINUE RELATED CONTEXT
```

The key boundary is:

> **Context continuity ≠ task restart ≠ authority continuity**

No source reviewed on 28 August establishes a universal recovery protocol, portable compensation object or automatic transfer of prior delegated authority into the successor Task

## 2｜Historical Continuity / 历史连续性

27 August established:

```text
cancel operation
≠ stop session
≠ delete retained state
≠ revert / compensate durable effect
```

That made termination and remediation separate lifecycle phases

But the W35 model still contained an ambiguous `resume`

28 August resolves that ambiguity structurally:

```text
OLD EXECUTION
→ terminal state
→ retained history / artifacts / side effects
→ reconciliation
→ NEW EXECUTION OBJECT
```

A runtime may preserve context, artifacts or state while the exact Task that failed or was cancelled remains terminal

Recovery therefore has to answer separately:

1. What historical execution object is closed?
2. What new execution object performs recovery or compensation?
3. What identity / delegation / policy evidence authorizes the new execution?

The third question remains open on 28 August and becomes the next research edge

## 3｜Critical Developments / 关键变化

### A2A — terminal Task, continuing context

A2A separates work-unit identity from contextual continuity

```text
old_task_id = historical execution evidence
new_task_id = new attempt / recovery work
context_id  = continuity across related work
```

This means a failed or canceled Task can remain stable historical evidence while later work continues under a new Task identity inside the same broader context

A2A does not thereby define:

- compensation semantics
- rollback semantics
- trust re-evaluation policy
- credential refresh rules
- incident ownership
- transfer of authority between old and new Tasks

Therefore:

> **New Task identity ≠ authorized recovery**

### MCP Tasks — cancellation is a coordination signal

The MCP 2026-07-28 release formalizes an extensions framework and moves long-running Tasks into that model

The detailed Tasks extension remains draft and defines cooperative cancellation semantics

A cancellation request may be acknowledged before the observable task state changes, and underlying work may finish in a racing terminal state

Therefore:

```text
cancel requested
≠ cancel observed
≠ execution physically stopped
≠ durable effects reconciled
```

The final MCP release establishes Tasks as an official extension family; the detailed extension lifecycle remains independently evolving

## 4｜Workstream Findings / 分任务发现

### F1 — History, Theory, Paradigms

Recovery requires separating contextual continuity from execution identity

```text
state/context continuity ≠ work-unit continuity
```

### F2 — Models, Algorithms, Multimodality

No model release changes the 28 August judgment

Model memory or semantic context cannot by itself define whether a terminated execution object is restartable or authorized

### F3 — Compute, Data, Infrastructure

Runtime state must distinguish at least:

- operation state
- task/session state
- retained local state
- durable external effects
- recovery execution identity

### F4 — Agents, Runtimes, Harnesses, Protocols

A2A supplies the strongest Task/context identity boundary

MCP Tasks supplies a durable asynchronous task-state and cancellation model

These are complementary protocol layers, not one unified recovery standard

### F5 — Evaluation, Safety, Governance, Standards

Recovery should remain auditable across terminal-state evidence and successor execution

But 28 August evidence does not yet prove fresh authorization / delegation rules for that successor Task

### F6 — Open Source, Industry, Economy, Society

Non-code Agent effects may require separate withdraw / supersede / compensate operations after the original Task is terminal

A new recovery Task does not automatically discover or reverse every prior effect

### F7 — Cross-System Synthesis

The emerging recovery chain is:

```text
INCIDENT / CANCELLATION
→ TERMINAL TASK RECORD
→ RESIDUAL-EFFECT INVENTORY
→ REMEDIATION PLAN
→ NEW RECOVERY TASK
→ CONTEXTUAL CONTINUITY
→ ? AUTHORITY / POLICY
→ RECOVERY WORK
→ FOLLOW-UP VALIDATION
```

The `?` is deliberate

## 6｜Changed Judgments / 修正的判断

### H1 — Runtime trust requires continuous re-evaluation
**STRONGLY STRENGTHENED**

A successor Task should not inherit stale trust merely because it shares context with the failed Task

### H2 — Revocation requires explicit enforcement points
**STRONGLY STRENGTHENED / REFINED**

### H3 — Artifact trust and workload identity remain distinct but correlated
**SUPPORTED**

### H4 — Short-lived identity does not replace policy revocation
**STRENGTHENED**

### H5 — Exception paths become lifecycle objects

### H8 — Relying-resource participation matters to revocation
**STRONG IMPLEMENTATION SIGNAL / unchanged**

### H9 — Explicit Agent-runtime termination is a first-class control primitive
**STRONGLY STRENGTHENED**

### H10 — Termination and remediation are separate lifecycle phases
**STRONGLY STRENGTHENED**

### H11 — Recovery requires a new execution identity boundary
**NEW / STRONG OPEN-PROTOCOL STRUCTURAL SIGNAL**

A2A terminal Tasks cannot be restarted while context can continue across multiple Tasks; MCP Tasks independently gives long-running work stable task identity and cooperative cancellation semantics

**Falsifier:** mature interoperable Agent systems consistently recover failed / cancelled work by transparently reactivating the same terminal execution object with unchanged authority and without creating a new auditable execution identity

## 7｜Stable Judgments / 稳定判断

```text
context continuity ≠ task restart
terminal task ≠ deleted history
cancellation intent ≠ proven termination
task ID ≠ authorization identity
new task ≠ inherited authority
recovery task ≠ automatic compensation
shared context ≠ shared credential
historical artifacts ≠ current execution permission
terminal task ≠ incident closure
```

The strongest stable principle is:

> **Preserve the old Task as evidence; make recovery a new auditable execution boundary**

## 8｜Uncertainties and Conflicts / 不确定与冲突

Public evidence still does not expose one portable recovery object binding:

```text
incident_id
→ original_task_id
→ terminal_state
→ residual_effect_inventory
→ remediation_plan
→ recovery_task_id
→ recovery_authority_evidence
→ remediation_actions
→ completion_evidence
→ follow-up_validation
```

Open conflicts / uncertainties include:

- whether recovery Tasks can formally reference the Tasks they repair or supersede
- whether one incident identifier can span A2A, MCP and vendor-local execution IDs
- whether successor Tasks require fresh delegation, fresh credential, fresh authorization decision, or some combination
- whether compensation can be a first-class interoperable Task
- whether a terminal Task can expose all committed external effects
- whether cancellation acknowledgment can be correlated with physical stop and side-effect reconciliation
- whether non-code outputs have equivalent withdraw / supersede / compensate states

## 9｜Watchlist / 下一轮观察点
