## 0｜Executive Judgment / 核心判断

W35 began with a difficult operational question:

> **What happens after admission when trust changes?**

Seven observation days now separate a nearly complete incident / recovery chain:

```text
24 Aug  admission-time trust → continuous runtime trust
25 Aug  trust change → relying-resource denial
26 Aug  resource / control decision → explicit runtime stop
27 Aug  stop → residual-state inventory → remediation
28 Aug  terminal task → distinct successor recovery task
29 Aug  successor request → authentication / authorization
30 Aug  primary-source recheck → no new maturity transition; boundaries survive settlement
```

Sunday does not create H12.

Current A2A specification still separates `contextId` from Task identity: a context can group multiple related Tasks and Messages while each Task remains a distinct stateful unit of work. Terminal Tasks are not a permission to resurrect the same execution object invisibly.

The same specification requires incoming requests to be authenticated and authorization to be scoped by the server's policy over authenticated identity. Its in-task authorization section is especially strong:

```text
TASK_STATE_AUTH_REQUIRED
≠ authorization for a particular operation
≠ automatic authorization of later messages
```

MCP Tasks independently keeps durable task identity and cooperative cancellation distinct; GitHub and Microsoft implementation evidence keeps stop, preserved state and resource-side denial distinct.

The W35 final judgment is therefore:

> **Context may preserve meaning across recovery, but execution identity, current authority, durable effects and remediation remain separately governable state.**

## 3｜Critical Developments / 关键变化

### 3.1 A2A task/context boundary remains stable

The current specification continues to model:

- `taskId` as a unique stateful unit of work
- `contextId` as a grouping mechanism across related Tasks / Messages
- terminal task states as terminal execution states rather than restart containers

This keeps:

> **Context continuity ≠ task restart**

### 3.2 A2A authorization boundary remains stable

The current security model requires authenticated requests and server-side authorization scoping.

For in-task authorization, the spec explicitly states that `TASK_STATE_AUTH_REQUIRED` does not itself authorize an operation; any resulting authorization scope / validity / revocation semantics must be defined by implementation, issuer or extension.

It also warns against assuming an authorization decision obtained in that state automatically covers later Task messages.

This keeps:

> **Context continuity ≠ authority continuity**

and:

> **Authorization event ≠ ambient future authority**

### 3.3 MCP cancellation remains coordination, not transactional rollback

MCP Tasks continues to model durable task identity while cancellation remains cooperative. A cancellation request is not equivalent to proof that every underlying effect stopped or was rolled back.

### 3.4 Product evidence still separates stop from residue

GitHub session stop can end future Agent work / the associated Actions run while preserving already-pushed commits.

Microsoft workload CAE can reject supported resource requests after relevant trust changes, but resource denial is not equivalent to global Agent-process termination.
