# Revocation Reaches the Resource / 撤销到达资源端
## Global AI Daily Research Report / 全球人工智能每日研究报告
### 2026-08-25

**Observation cut-off / 观察截止：2026-08-25 06:40 CST**

## 0｜Executive Judgment / 核心判断

W35 opened by separating admission-time trust from live runtime trust

Today adds a more concrete enforcement path

Microsoft Entra Continuous Access Evaluation for workload identities shows that a revocation event can propagate beyond the identity issuer into a participating resource provider

For supported workload-identity flows:

```text
WORKLOAD IDENTITY
→ ACCESS TOKEN
→ RESOURCE REQUEST
→ REVOCATION / RISK / POLICY CHANGE
→ RESOURCE RE-EVALUATION
→ TOKEN REJECTED
→ 401 CLAIMS CHALLENGE
→ NEW TOKEN REQUEST
→ CONDITIONS RE-EVALUATED
```

This is important because it turns yesterday's abstract `policy decision → enforcement point` requirement into a real resource-side denial path

But it does **not** prove universal Agent runtime revocation

Current Microsoft documentation explicitly limits workload-identity CAE to supported single-tenant service principals and Microsoft Graph; third-party SaaS, multitenant applications and managed identities are outside the current scope

Therefore today's durable refinement is:

> **Revocation is not only an issuer event — a relying resource must be able to consume and enforce the changed trust state**

And the hard boundary remains:

> **Resource denial ≠ Agent-process termination**

A resource may reject a token while the Agent process remains alive, continues using other credentials, calls other resources, or executes local actions

## 1｜From policy signal to resource denial / 从策略信号到资源拒绝

NIST Zero Trust models a PDP deciding whether an active session should continue, be limited or be revoked, and a PEP enforcing that decision

Microsoft CAE provides a concrete implementation pattern for workload identity access:

- service principal opts into CAE capability
- Microsoft Entra issues a CAE-enabled token
- supported resource provider evaluates the token against revocation events and policy changes
- service-principal disable, delete or high-risk state can invalidate continued access
- resource rejects the request with `401`
- client receives a claims challenge and must request a new token
- conditions are evaluated again before access can continue

The architecture therefore becomes:

```text
TRUST SIGNAL
→ IDENTITY / POLICY SERVICE
→ EVENT PROPAGATION
→ RELYING RESOURCE
→ ENFORCEMENT
→ CLIENT RE-AUTH / RE-EVALUATION
```

## 2｜Agent relevance / 与 Agent 的关系

Microsoft Entra Conditional Access for Agents makes the subject/audience relationship explicit

Depending on the flow:

- the user may be represented together with the calling Agent
- an autonomous Agent may itself be the subject
- an Agent user account may be the subject
- different resources normally receive distinct audience-specific access tokens

Some resources can additionally support Continuous Access Evaluation

This makes CAE relevant to the W35 Agent question, but it remains incorrect to claim that every Agent runtime or every Agent resource supports near-real-time revocation

## 3｜The propagation problem becomes resource-specific / 撤销传播开始显露资源边界

Yesterday's question was:

`Can trust changes reach an already-running workload?`

Today the answer becomes more precise:

```text
IDENTITY TRUST CHANGE
        ↓
SUPPORTED RESOURCE A
→ deny / challenge

UNSUPPORTED RESOURCE B
→ separate lifecycle

LOCAL AGENT PROCESS
→ may still be running
```

This means runtime revocation is not one binary switch

It may require coordination across:

- identity issuer
- resource provider
- token / credential lifecycle
- Agent runtime
- tool / MCP / API boundary
- delegated authority
- local process / workload scheduler

### H1 — Runtime trust requires continuous re-evaluation

**STRENGTHENED**

CAE shows a production mechanism where trust-relevant events are evaluated after token issuance rather than waiting for ordinary expiry

### H2 — Revocation requires an explicit enforcement point

**STRONGLY STRENGTHENED**

The supported resource provider becomes an identifiable enforcement point that can reject the token and force re-evaluation

### H3 — Artifact trust and workload identity remain distinct but correlated

**SUPPORTED / unchanged**

### H4 — Short-lived identity does not replace policy revocation

**STRENGTHENED**

Microsoft CAE explicitly addresses the problem that waiting for token expiry is insufficient for timely policy enforcement

### H5 — Exception paths become lifecycle objects

**OPEN**

No new evidence today resolves exception expiry or break-glass governance

### H6 — Non-code Agent outputs need equivalent lifecycle boundaries

**OPEN**

Resource-side denial does not yet provide publication / supersession / revocation semantics for non-code outputs

### H7 — End-to-end correlation becomes incident infrastructure

**SUPPORTED / strengthened context**

Resource denial, claims challenge and token re-evaluation add new events that incident reconstruction must correlate

### H8 — Relying-resource participation becomes part of revocation infrastructure

**NEW / STRONG IMPLEMENTATION SIGNAL**

A trust change only produces runtime effect where a participating resource can receive or infer that change and enforce it

**Falsifier:** a portable issuer-only mechanism reliably revokes heterogeneous Agent access across independent resources without resource-side participation or equivalent enforcement

## 5｜Durable rules / 耐久候选规则

```text
revocation event ≠ propagated revocation
issuer decision ≠ resource enforcement
resource denial ≠ Agent-process termination
401 claims challenge ≠ global Agent shutdown
identity disable ≠ cross-resource authority revocation
one resource's CAE support ≠ universal runtime support
continuous access evaluation ≠ continuous task correctness
```

## 6｜Critical scope calibration / 范围校准

Microsoft workload-identity CAE currently has important limitations

- Microsoft Graph is the supported resource provider described in current documentation
- only single-tenant service principals are supported
- third-party SaaS and multitenant apps are out of scope
- managed identities are not supported
- CAE focuses on specified revocation/risk/policy events

Therefore this is strong implementation evidence for a **revocation propagation pattern**, not evidence that the global Agent ecosystem has solved runtime revocation

## 7｜What to watch next / 下一步

1. Agent-specific Conditional Access + CAE combinations beyond Microsoft Graph
2. MCP / A2A resources consuming equivalent revocation events or claims challenges
3. resource denial triggering Agent runtime cancellation or safe degradation
4. delegated-user authority revocation propagating independently from Agent identity
5. cross-resource correlation when only some resources support continuous evaluation
6. policy exception / break-glass behavior under live revocation
7. non-code action/output rollback after access is revoked
