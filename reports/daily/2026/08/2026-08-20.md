## 0｜Executive Judgment / 核心判断

今天没有必要为了 8 月 20 日制造一个“凌晨刚发布”的 Agent 新闻

W34 前三天已经依次把治理从 workspace 推进到 session evidence，再推进到 commit / PR / review 的 durable provenance

今天真正值得补上的下一段，是**源码变更之后的构建产物来源链**

GitHub Artifact Attestations 当前能够为软件构建生成密码学签名的 provenance claim，并记录与 artifact 关联的 workflow、repository、organization、environment、commit SHA 与 triggering event；GitHub 使用 Sigstore 生成和验证这些 attestation，公共仓库还可把 bundle 写入公开 transparency log

这使昨天的链条继续延伸：

```text
TASK / ISSUE
→ AGENT SESSION
→ SESSION LOGS
→ AGENT-AUTHORED COMMIT
→ PULL REQUEST
→ REVIEW / CHECKS
→ MERGE DECISION
→ BUILD WORKFLOW
→ ARTIFACT DIGEST
→ SIGNED ATTESTATION
→ VERIFY / POLICY DECISION
→ DEPLOY / CONSUME
```

今天的核心判断是：

> **Agent provenance 如果要真正进入软件交付链，不能停在“谁改了代码”，还需要回答“哪份构建产物由哪次已知源码和工作流产生”**

但边界必须同时写死：

> **Artifact attestation ≠ security guarantee**

GitHub 官方明确说明，attestation 建立的是来源与完整性证据，不自动证明 artifact 本身安全；验证方仍然需要定义自己的 policy criteria，并基于 attestation 内容作风险决策

## 1｜From source change to produced artifact / 从源码变更到产物

**FACT** — GitHub Artifact Attestations 可以创建密码学签名声明，绑定 artifact 与产生它的 workflow、repository、environment、commit SHA 和 triggering event

**FACT** — GitHub 使用 Sigstore 生成这些 attestation；公共仓库的 Sigstore bundle 可进入不可变的公开 transparency log

**FACT** — GitHub 文档把 artifact attestation 本身定位为 SLSA v1.0 Build Level 2 能力，并说明可结合 reusable workflows 达到更高的 Build Level 3 条件

**ANALYSIS** — W34 昨天形成的 `session → commit → PR → merge` provenance chain 仍然只描述了 source change provenance

软件真正被使用时，最终消费者面对的是 binary、package、container image 或 manifest

因此需要一个新的边界：

```text
SOURCE PROVENANCE
commit / PR / merge

↓ build

ARTIFACT PROVENANCE
artifact digest / workflow / source SHA / attestation
```

## 2｜Agent provenance and build provenance are different / Agent 来源链与构建来源链不同

一个 Agent-authored commit 可以回链到 session logs

但这并不回答：

- 哪个 workflow 构建了最终 artifact
- artifact 是否对应这个 commit SHA
- build environment 是什么
- build 是否经过预期触发事件
- artifact 是否在构建后被替换

反过来，artifact attestation 也不会告诉你 Agent 为什么做出某个代码修改

因此今天形成新的稳定边界：

> **Session provenance ≠ source provenance ≠ build provenance**

三层需要相关联，而不能互相替代

## 3｜Verification becomes a consumption boundary / 验证进入消费边界

GitHub 文档明确建议消费者对 attestation 做验证

这使供应链末端形成另一层状态：

```text
artifact exists
≠
artifact has attestation
≠
attestation verifies
≠
artifact satisfies local policy
≠
artifact is authorized to deploy
```

尤其最后两层不能被密码学来源证明自动覆盖

**Durable candidate:**

> **Cryptographic provenance ≠ deployment authorization**

## 5｜Workstream Findings / 分任务发现

### F1 History and theory

Automation governance is moving from action history toward evidence continuity across lifecycle boundaries

The important abstraction is no longer one Agent session, but a chain whose meaning survives from task intent into the consumed artifact

### F2 Models and algorithms

No same-day model event before cut-off changes the model trajectory

Stronger coding and computer-use capability increases the importance of distinguishing model-generated source from the independently verifiable artifact produced later

### F3 Infrastructure

Sigstore, transparency logs, artifact digests, OIDC identity and attestations become part of the infrastructure needed to carry provenance into build and deployment systems

### F4 Agentic systems

Agent runtime provenance should eventually correlate session identity, delegated user, generated source, build source SHA and delivered artifact digest

No evidence today shows a universal schema that does this end to end

### F5 Evaluation and governance

Verification must answer at least two separate questions:

```text
Did this artifact come from the claimed source and build process?
≠
Should this artifact be trusted and deployed here?
```

The first is provenance verification

The second is policy / risk judgment

### F6 Ecosystem and society

Open provenance infrastructure can reduce bilateral trust requirements between producer and consumer, but it also raises expectations that Agent-produced outputs carry machine-readable evidence rather than relying on vendor reputation

### F7 Synthesis

W34 now has a four-stage evidence chain:

```text
PRE-EXECUTION GOVERNANCE
→ SESSION EVIDENCE
→ DURABLE SOURCE CHANGE
→ ATTESTED BUILD ARTIFACT
```

The next unresolved step is whether the same chain survives actual deployment, runtime rollback, incident response and non-code Agent outputs

## 6｜New Durable Candidates / 新耐久候选规则

> **Session provenance ≠ source provenance ≠ build provenance**

> **Source review ≠ artifact integrity**

> **Artifact attestation ≠ security proof**

> **Signed attestation ≠ policy acceptance**

> **Verification ≠ authorization to deploy**

## 7｜Status Calibration / 状态校准

- artifact attestation ≠ Agent-specific provenance standard
- Sigstore usage ≠ complete cross-platform Agent governance
- SLSA build level ≠ software safety certification
- transparency log ≠ semantic correctness
- verified source/build provenance ≠ valid delegated authority
- verified artifact ≠ approved deployment

## 8｜Watchlist / 下一轮观察点
