# Runtime Becomes Stoppable / 运行时开始可终止

## 0｜Executive Judgment / 核心判断

W35 began by asking whether trust can stay synchronized after execution begins

24 August established continuous runtime trust as the problem

25 August supplied a concrete propagation path from trust change to relying-resource denial

Today closes one more gap:

> **Agent runtimes increasingly expose an explicit stop / cancel control primitive**

GitHub Copilot agent sessions can be stopped from the session viewer. GitHub states that stopping a session ends the associated GitHub Actions run while preserving commits already pushed

Microsoft Foundry hosted agent sessions expose REST / SDK stop operations. Stopping a hosted session terminates its running compute while preserving the persistent filesystem volume so the session can later be resumed

The runtime lifecycle can therefore be separated more precisely:

```text
TRUST / RISK CHANGE
→ RESOURCE DENIAL OR OPERATOR / CONTROL DECISION
→ RUNTIME STOP CONTROL
→ RUNNING COMPUTE ENDS
→ PERSISTED STATE / ARTIFACTS MAY REMAIN
→ REVIEW / RESUME / RESTART / REVOKE
```

This is stronger evidence than yesterday's resource denial alone

But the key unresolved edge remains:

> **Explicit stop control ≠ automatic trust-signal-to-stop propagation**

Current public evidence does not show a universal mechanism where an identity-risk event, CAE claims challenge, artifact-attestation revocation, delegated-authority change or MCP/A2A trust signal automatically invokes a heterogeneous Agent runtime's stop primitive

## 1｜GitHub — session stop is a runtime control / GitHub：停止会话是真实运行时控制

GitHub's current Agent session management documentation explicitly supports `Stop session`

Stopping a Copilot coding-agent session:

- stops the Agent from continuing the task
- ends the associated GitHub Actions run
- preserves commits that were already pushed
- leaves the past session/log evidence available for review

This gives W35 a concrete distinction:

```text
STOP FUTURE EXECUTION
≠
ROLL BACK PAST EFFECTS
```

A stopped session may already have produced commits, external observations or other durable state

Therefore cancellation is a lifecycle control, not retroactive erasure

## 2｜Microsoft Foundry — stop compute, preserve state / Microsoft Foundry：终止计算，保留状态

Microsoft Foundry hosted agent sessions expose session-management APIs including a stop operation

The documented semantics are explicit:

- `:stop` / `stop_session()` terminates running compute
- persistent filesystem volume remains
- the session can later be resumed
- stopping an already-stopped session succeeds without error
- Header isolation requires the same isolation key used to create the session
- Entra isolation scopes the stop operation to the calling identity

This provides a second runtime implementation with different product semantics but the same structural idea:

> **running Agent state can have an explicit lifecycle transition into STOPPED without becoming DELETED**

## 3｜The control chain is now longer / 控制链继续延长

W35 can now distinguish four different layers:

```text
1. TRUST STATE
   identity / risk / policy / delegation

2. RESOURCE ENFORCEMENT
   allow / deny / claims challenge

3. AGENT RUNTIME CONTROL
   continue / steer / stop / cancel

4. PERSISTED EFFECTS
   commits / files / external mutations / durable outputs
```

These layers may be connected, but they are not interchangeable

Yesterday's Microsoft CAE evidence grounds layer 2

Today's GitHub and Microsoft Foundry evidence grounds layer 3

The missing engineering object is the policy and correlation path that safely maps layer 1 or 2 into layer 3 while accounting for layer 4

## 4｜Why stop semantics matter / 为什么停止语义重要

A runtime stop can mean several different things:

- stop current model generation
- cancel one tool call
- stop background workers or subagents
- terminate one session compute process
- terminate the whole Agent task
- prevent future resume

Current products expose some of these controls, but not one universal semantic model

This matters because an incident response system needs to know exactly what became inactive and what remains live

For example:

```text
RESOURCE A DENIED
but
RESOURCE B TOKEN STILL VALID
and
LOCAL TOOL STILL RUNNING
and
PUSHED COMMIT STILL EXISTS
```

A safe response cannot infer global termination from a single denied request
