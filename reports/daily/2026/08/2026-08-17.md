# Governance Reaches the Workspace / 治理进入工作空间
## Global AI Daily Research Report / 全球人工智能每日研究报告
### 2026-08-17

**Observation cut-off / 观察截止：2026-08-17 06:21 CST**

## 0｜Executive Judgment / 核心判断

今天是 W34 开周日

没有发现观察截止前足以改写 W33 信任栈结论的同日重大标准或模型发布，因此今天不制造“8 月 17 日新热点”

W33 建立了一个耐久判断：Agent capability 可以越来越原生，但 accountable agency 仍然需要 discovery、identity、provenance、delegation、trust boundary、revocation、audit 与 evaluation 组成的显式信任栈

今天把这一判断放进真实产品运行面后，新的结构开始清晰：**信任栈正在进入 workspace / enterprise product controls，而不再只存在于 IAM、协议草案或安全架构文档中**

当前 OpenAI Workspace Agents 文档已经把以下控制拆成独立产品对象：

- draft 与 published version 分离
- workspace / role-based access control
- schedule 与 API trigger
- scoped Workspace Agent access token
- end-user account 与 agent-owned account 两类连接身份
- write-action approval
- connector action constraints
- owner / editor / chat-only access
- group access与版本历史

GitHub Agent Control Plane 同时提供 agent session activity、audit log、enterprise AI policy 与 MCP allowlist；Microsoft Entra Agent ID 则把 human sponsor、owner、access package、expiration 与 Conditional Access 放进 Agent identity 生命周期治理

因此今天的结构性判断是：

> **Agent governance 正从“外围安全控制”进入 Agent 产品本身的发布、连接、触发、审批与生命周期结构**

这不代表不同平台已经形成统一治理模型，也不代表 workspace-level policy 可以替代开放协议层的身份与跨域信任

## 1｜From trust stack to governed execution / 从信任栈到受控执行

W33 模型：

```text
capability
→ discovery
→ identity
→ provenance
→ delegation
→ trust boundary
→ action
→ audit / revocation
```

W34 开周把它压到执行面：

```text
DRAFT DEFINITION
→ PUBLISH BOUNDARY
→ WHO MAY RUN
→ WHICH CONNECTION IDENTITY
→ WHICH TOOLS / CONNECTORS
→ WRITE APPROVAL / ACTION CONSTRAINT
→ SCHEDULE / API / CHANNEL TRIGGER
→ EXECUTION
→ AUDIT / ANALYTICS / REVOCATION
```

新的问题不再只是“有没有权限”

而是：**权限、版本、连接身份、触发方式与运行时批准能否一起形成可解释的 execution envelope**

## 2｜Published state becomes operationally meaningful / 发布态开始成为运行边界

OpenAI Workspace Agents 当前区分 shared draft 与 published version

Existing users continue using the latest published version until a new draft is explicitly published；schedule 与 API trigger 的变更也只有在 published agent 上才会生效

这给出一个重要的运行时边界：

> **Editable definition ≠ live executable state**

这与软件发布治理非常接近，但 Agent 还额外包含模型、instructions、skills、connectors、connection identities 与 write approvals

因此 W34 必须观察 Agent configuration change 如何被版本化、审核、发布和回滚

## 3｜Connection ownership becomes an authority dimension / 连接所有权成为权限维度

Workspace Agents 当前区分：

- end-user account — 每个运行者以自己的账号连接
- agent-owned account — 所有运行者共享一个 Agent 连接

这不是单纯的登录体验差异

它直接决定：

```text
WHO INVOKES
≠
WHO AUTHENTICATES TO THE DOWNSTREAM SYSTEM
```

共享连接会让 Agent 的下游权限与运行者身份发生分离，因此需要更严格的 least privilege、audience control、write approval 与 audit

## 4｜Approval and constraints are separate controls / 批准与约束不是同一层

Workspace Agents 当前把 write-action approval 与 Connector Action Constraints 分开

write approval 控制“某个写操作是否需要确认”

action constraint 控制“Agent 可以请求 connector 做什么”

而官方文档同时明确：constraints 限制 action inputs，但不负责过滤 connector 返回的数据

这形成 W34 一个重要边界：

> **Action constraint ≠ output / data-return governance**

未来需要观察读取范围、返回数据、敏感数据外泄与 write authority 如何组成完整 policy closure

## 5｜Human accountability survives automation / 自动化没有消灭人类责任主体

Microsoft Entra Agent ID 把 owner 与 sponsor 分开：owner 负责技术管理，sponsor 对 Agent purpose、lifecycle 和 access decisions 承担业务责任

access package 还可以通过 Agent 自身、sponsor 代申请或 admin 直接分配三条路径获取，并可设置到期与再次审批

GitHub Agent Control Plane 则在 audit 中区分 `actor_is_agent` 与 agent acting on behalf of 的 user / user_id

因此今天保留 W33 的一个核心原则，并进一步产品化：

> **Autonomous execution does not eliminate accountable human / organizational ownership**

## 6｜W34 Opening Questions / W34 开周问题

1. draft → published 是否会成为跨 Agent 平台的通用运行治理边界
2. end-user identity 与 agent-owned identity 如何映射到 delegation 与 audit
3. write approval、parameter constraint、data-return control 是否最终形成三个独立 policy layers
4. schedule / API / Slack / IDE 等不同 trigger 是否共享一致的 authority envelope
5. human sponsor / owner 模型是否在更多 Agent 平台出现
6. workspace governance 如何映射到 MCP / A2A / open Web identity，而不是锁在单厂商控制面
7. Agent analytics 能否从 run counts 进入 failure、recovery、revocation 与 authority-trace evidence

## 7｜Status Boundaries / 状态边界

- product control ≠ open standard
- RBAC ≠ runtime action authorization
- write approval ≠ data-return governance
- agent-owned connection ≠ user delegation
- published configuration ≠ correct behavior
- audit visibility ≠ task correctness
- enterprise control plane ≠ cross-domain trust interoperability
