# Durable Tasks Sharpen the Stop/Recovery Boundary / 持久任务进一步刻画停止与恢复边界
## Global AI Daily Research Report / 全球人工智能每日研究报告
### 2026-09-17

## 0｜Executive Judgment / 核心判断
本轮完成 F1–F7 全量复核。MCP `SEP-2663` 当前仍为 Final / Extensions Track，但其 normative text 提供了独立于 A2A 的更精确执行与安全边界：task 创建在返回前必须 durable；每个 task-related request 必须重新执行 authentication/authorization checks；`tasks/cancel` 只是 cooperative intent + ack，observable state 可暂不变化，最终甚至不保证进入 `cancelled`。

这加强了“durable execution state 已明确，而 runtime stop / rollback / remediation 仍不是同一件事”的证据边界，但没有证明 committed external effects、rollback/compensation obligations、successor authority 或 recovery completion proof。W38 hypotheses 保持 `OPEN`；本轮是新的独立 MCP source-lineage evidence，不是对 A2A 的重复计数。

## 1｜Research Scope / 今日研究范围
检查 F1–F7，保持 capability > discovery > identity > authority > execution > runtime trust > revocation > recovery > governance，并使用 SECURITY / EXECUTION / DURABLE EFFECTS / RECOVERY 四层模型。

## 2｜Historical Continuity / 历史连续性
2026-09-16 的 A2A authority-boundary evidence 保留。今天 MCP evidence 独立显示：task durability、per-request authz 与 cancellation acknowledgement 已规范化，但这些仍不等于 portable recovery contract。

## 3｜Critical Developments / 关键变化
- MCP task creation: server MUST NOT return `CreateTaskResult` until the task is durably created and resolvable via `tasks/get`.
- MCP security: servers MUST perform authentication and authorization checks on each task-related request.
- MCP cancellation: `tasks/cancel` signals intent; cancellation is cooperative/eventually consistent; stop is not guaranteed and terminal `cancelled` is not guaranteed.
- `SEP-2663` remains Final / Extensions Track and explicitly expects further incubation before intended core promotion.
- NIST NCCoE Agent Identity and Authorization remains `Reviewing Comments`.
- A2A recovery-lineage/successor-authority gaps remain unresolved in the checked specification.

## 4｜Workstream Findings / 分任务发现
F1–F3: no material tracked transition.
F4: MCP provides stronger durable-task lifecycle semantics, but task identity/state is not recovery authority.
F5: per-task-request authz is explicit; continuous/portable authorization lifecycle, break-glass, successor authority and recovery acceptance remain unverified.
F6: `Protocol Publication != Operational Maturity`; SEP Final does not imply core promotion or deployment maturity.
F7: `Resource Denial != Runtime Stop`; `Runtime Stop != Rollback`; cancellation acknowledgement != actual stop remains directly supported by MCP semantics.

## 5｜Cross-System Analysis / 跨系统分析
A2A and MCP now independently expose stronger execution/authorization surfaces. MCP additionally requires durable task creation and per-request authz, while cancellation remains cooperative. Neither checked lineage closes the portable DURABLE EFFECTS→RECOVERY contract.

## 6｜Changed Judgments / 修正的判断
No hypothesis state closes. H38-3/H38-4 receive independent MCP evidence that sharpens their boundary: durable async execution and repeated authorization checks can mature without portable rollback/compensation or exception/recovery lifecycle semantics.

## 7｜Stable Judgments / 稳定判断
`Capability != Deployability`; `Discovery != Authorization != Invocation`; `Identity != Credential != Authority`; `Admission != Continuous Authorization`; `Resource Denial != Runtime Stop`; `Runtime Stop != Rollback`; `Termination != Remediation`; `Context Continuity != Authority Continuity`; `referenceTaskIds != typed recovery lineage`; `Task reference != Task authority`.

## 8｜Uncertainties and Conflicts / 不确定与冲突
Committed external effects, retained-state obligations beyond task state, rollback/compensation, successor authority, exception/break-glass lifecycle, typed recovery lineage and portable recovery completion proof remain unresolved.
