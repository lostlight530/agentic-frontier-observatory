## 0｜Current Weekly Judgment / 当前周度判断

W34 proved that machine-verifiable evidence can participate in runtime admission

W35 asks the harder question:

> **Can a trust change alter the state of something that is already active?**

The week began by separating admission-time trust from live runtime trust

```text
ADMISSION-TIME
artifact provenance
→ policy evaluation
→ admit / reject

RUNTIME
workload identity
→ telemetry / environment
→ continuous policy evaluation
→ continue / limit / revoke
```

25 August adds an important implementation refinement

Microsoft Entra Continuous Access Evaluation for workload identities shows that, in supported scenarios, a resource provider can enforce changed trust state after token issuance by rejecting the token and forcing a claims challenge / fresh evaluation

```text
TRUST EVENT
→ IDENTITY / POLICY SERVICE
→ EVENT PROPAGATION
→ RELYING RESOURCE
→ DENY / CLAIMS CHALLENGE
→ TOKEN RE-EVALUATION
```

This strengthens the weekly direction without closing the problem

> **Resource denial ≠ Agent-process termination**

## 1｜W35 Hypothesis Progress / 假设进展

### H1 — Runtime trust requires continuous re-evaluation

**STRENGTHENED**

NIST supplies the general session model; Microsoft CAE supplies a constrained production mechanism where trust events are evaluated after token issuance

### H2 — Revocation requires an explicit enforcement point

**STRONGLY STRENGTHENED**

A supported relying resource can reject the token and force re-evaluation

### H3 — Artifact trust and workload identity remain distinct but correlated

**SUPPORTED / unchanged**

Today's evidence concerns live identity/access state rather than build provenance

### H4 — Short-lived identity does not replace policy revocation

**STRENGTHENED**

CAE exists specifically because waiting for ordinary token expiry is insufficient for timely policy response

### H5 — Exception paths become lifecycle objects

**OPEN**

No new evidence closes break-glass / temporary exception semantics

### H6 — Non-code Agent outputs need equivalent lifecycle boundaries

**OPEN**

Resource access denial remains different from revoking a durable document, ticket, CRM mutation or dataset release

### H7 — End-to-end correlation becomes incident infrastructure

**SUPPORTED / strengthened context**

Revocation events, resource rejection, claims challenges and fresh token decisions add additional events that incident reconstruction must correlate

### H8 — Relying-resource participation becomes part of revocation infrastructure

**NEW / STRONG IMPLEMENTATION SIGNAL**

A trust event has runtime effect only where a resource or equivalent enforcement surface can consume and enforce the changed state

**Falsifier:** a portable issuer-only mechanism reliably revokes heterogeneous Agent access across independent resources without resource-side participation or equivalent enforcement

## 2｜Monday Evidence Baseline / 24 August

### GitHub — admission and evidence lifecycle

Artifact attestations can participate in Kubernetes admission policy and can later be deleted

**Boundary:** attestation deletion does not prove automatic termination of already-running workloads

### NIST — continuous session evaluation

NIST Zero Trust models continued evaluation of active sessions and permits continue / limit / revoke decisions through PDP / PEP enforcement

**Boundary:** general access-control architecture, not an Agent-specific standard

### SPIFFE — live workload identity

Short-lived workload credentials and automatic rotation make live identity state dynamic

**Boundary:** workload identity ≠ delegated Agent authority

## 3｜Tuesday Evidence / 25 August

### Microsoft Entra — CAE for workload identities

For supported workload identities and resources:

1. service principal obtains a CAE-enabled token
2. resource provider evaluates token against revocation events / policy changes
3. service-principal disable, delete or high risk can invalidate continued access
4. resource rejects the request with `401` and a claims challenge
5. client requests a new token
6. conditions are evaluated again

### Microsoft Entra — Conditional Access for Agents

Agent access is explicitly subject/audience scoped; delegated user + Agent, autonomous Agent, or Agent user account can occupy different subject roles, and resources usually receive audience-specific tokens

### Scope boundary

Current workload-identity CAE documentation is limited to specified single-tenant service principals and Microsoft Graph; third-party SaaS, multitenant apps and managed identities are outside the described support scope

Therefore:

> implementation pattern ≠ universal Agent revocation fabric

## 4｜Research Priorities / 本周优先问题

1. resource denial → Agent runtime cancellation or safe degradation
2. CAE-style revocation beyond one provider / resource ecosystem
3. artifact provenance ↔ workload identity ↔ delegated authority mapping
4. cross-resource revocation when only some resources support continuous evaluation
5. Agent / MCP / A2A equivalents of claims challenge or event-driven revocation
6. break-glass / exception expiry and audit
7. end-to-end correlation across issuer → resource → Agent runtime → durable outcome
8. non-code publication/admission/revocation mechanisms

## 5｜Evidence Discipline / 证据纪律

```text
admission ≠ continuous authorization
revocation event ≠ propagated revocation
issuer decision ≠ resource enforcement
resource denial ≠ Agent-process termination
401 claims challenge ≠ global Agent shutdown
credential rotation ≠ authority revocation
workload identity ≠ delegated Agent authority
one resource's CAE support ≠ universal runtime support
telemetry ≠ incident reconstruction
```
