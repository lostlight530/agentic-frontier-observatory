# Live Trust / 持续信任
## Global AI Weekly Research — 2026-W35 Opening
### Watch window: 2026-08-24 → 2026-08-30

> **From Executable Governance to Runtime Trust Propagation**  
> **从可执行治理，走向运行时信任传播**

## 0｜Opening Judgment / 开周判断

W34 proved that machine-verifiable evidence can enter real execution paths and participate in runtime admission

W35 inherits the unresolved edge:

> **Can a trust change alter the state of something that is already running?**

This week therefore separates admission-time trust from live runtime trust

```text
ADMISSION-TIME
artifact provenance
→ policy evaluation
→ admit / reject

RUNTIME
workload identity
→ telemetry / environment
→ continuous policy evaluation
→ continue / limit / revoke
```

GitHub supplies a concrete admission and attestation-lifecycle model. NIST Zero Trust supplies a general runtime architecture where policy decisions may continue, limit, or revoke active sessions. SPIFFE supplies short-lived, automatically rotated workload identity

These are complementary references, not one unified Agent standard

## 1｜W35 Working Hypotheses / 工作假设

### H1 — Runtime trust requires continuous re-evaluation

Long-lived autonomous execution cannot be governed safely by admission-time verification alone

**Falsifier:** mature long-running Agent deployments work safely with no equivalent ongoing trust evaluation

### H2 — Revocation requires an explicit enforcement point

A trust signal becomes operational only when an enforcement component can constrain or terminate the affected session/workload

**Falsifier:** runtime revocation works reliably without an identifiable enforcement mechanism

### H3 — Artifact trust and workload identity remain distinct but correlated

Build provenance and live identity answer different questions and should remain separable while sharing correlation metadata

**Falsifier:** a single portable primitive safely represents both without semantic loss

### H4 — Short-lived identity does not replace policy revocation

Credential rotation reduces exposure but does not automatically revoke artifact trust, delegated authority, or business permission

**Falsifier:** short-lived identity alone proves sufficient for the relevant runtime trust lifecycle

### H5 — Exception paths become lifecycle objects

Break-glass and temporary bypasses require owner, reason, scope, expiry and audit semantics

**Falsifier:** mature deployments safely use unstructured exceptions without persistent governance blind spots

### H6 — Non-code Agent outputs need equivalent lifecycle boundaries

Documents, tickets, CRM changes, infrastructure state and datasets require publication/admission/revocation semantics comparable to code artifacts

**Falsifier:** non-code autonomous outputs remain safely governed without equivalent durable boundaries

### H7 — End-to-end correlation becomes incident infrastructure

Incident response requires reconstructing a chain across Agent definition, identity, delegation, session, artifact/output and runtime state

**Falsifier:** incidents can be reliably reconstructed without cross-layer correlation

## 2｜Monday Evidence Baseline / 周一证据基线

### GitHub — admission and evidence lifecycle

Artifact attestations can be verified by a Kubernetes admission controller before deployment. Attestations can also be deleted later

**Boundary:** admission enforcement does not establish automatic termination of already-running workloads

### NIST — continuous session evaluation

NIST Zero Trust deployment guidance models ongoing policy evaluation and allows an active session to be continued, limited or revoked when trust-relevant information changes

**Boundary:** this is general access-control architecture, not an Agent-specific standard

### SPIFFE — live workload identity

SPIFFE workload identity uses short-lived X.509-SVIDs, automatic key/certificate rotation and refreshed trust bundles

**Boundary:** workload identity does not encode Agent delegation, artifact provenance or business authority

## 3｜Research Priorities / 本周优先问题

1. Evidence revocation → runtime enforcement propagation
2. Artifact provenance ↔ workload identity mapping
3. Agent identity / delegation ↔ runtime policy mapping
4. Break-glass / exception expiry and audit
5. Correlation IDs across Agent → tool → artifact → runtime
6. Already-running workload response to trust changes
7. Non-code publication/admission/revocation mechanisms
8. MCP/A2A/Web identity interaction with runtime enforcement

## 4｜Evidence discipline / 证据纪律

```text
admission ≠ continuous authorization
credential rotation ≠ authority revocation
attestation deletion ≠ workload termination
workload identity ≠ delegated Agent authority
policy decision ≠ enforcement
telemetry ≠ incident reconstruction
exception ≠ permanent bypass
```
