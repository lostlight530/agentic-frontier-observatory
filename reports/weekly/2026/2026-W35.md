## 0｜Current Weekly Judgment / 当前周度判断

W35 began with one unresolved question from W34:

> **Can a trust change alter the state of something that is already active?**

Five days now expose a deeper runtime lifecycle

```text
24 Aug  continuous runtime trust
25 Aug  trust change → relying-resource denial
26 Aug  explicit Agent runtime stop
27 Aug  stop → residual-state inventory → remediation
28 Aug  terminal task → new recovery-task identity → contextual continuity
```

The weekly model is now:

```text
TRUST / INCIDENT SIGNAL
→ RESOURCE DENIAL
→ OPERATION / TASK CANCELLATION
→ SESSION / COMPUTE STOP
→ RESIDUAL STATE INVENTORY
→ TERMINAL TASK RECORD
→ DELETE / REVERT / COMPENSATE / REVOKE
→ NEW RECOVERY TASK
→ FRESH AUTHORITY / POLICY
→ FOLLOW-UP VALIDATION
```

The Friday refinement is:

> **Recovery should preserve the old terminal task as evidence and create a new auditable execution boundary**

This does not mean one universal recovery protocol exists

## 1｜W35 Hypothesis Progress / 假设进展

### H1 — Runtime trust requires continuous re-evaluation

**STRONGLY STRENGTHENED**

A recovery task should not inherit stale trust merely because it shares context with the failed/cancelled task

### H2 — Revocation requires explicit enforcement points

**STRONGLY STRENGTHENED / REFINED**

W35 now distinguishes resource denial, operation cancellation, task cancellation, runtime termination and recovery-task creation as separate control surfaces

### H3 — Artifact trust and workload identity remain distinct but correlated

**SUPPORTED**

Artifacts and history can survive a terminal task and inform later work without becoming authority for that later work

### H4 — Short-lived identity does not replace policy revocation

**STRENGTHENED**

Task identity, credential state and authorization remain distinct

### H5 — Exception paths become lifecycle objects

**OPEN / stronger pressure**

Recovery tasks create a natural place for owner, scope, reason, expiry and break-glass evidence, but no portable schema was found today

### H6 — Non-code Agent outputs need equivalent lifecycle boundaries

**STRENGTHENED PRESSURE**

Recovery work may need to supersede or compensate already-published documents, messages, tickets, CRM changes, datasets or infrastructure state

### H7 — End-to-end correlation becomes incident infrastructure

**STRONGLY STRENGTHENED**

Incident reconstruction now needs at least:

```text
original task ID
→ terminal state
→ residual effects
→ recovery task ID
→ shared context / incident reference
→ fresh authority
→ remediation result
```

### H8 — Relying-resource participation becomes part of revocation infrastructure

**STRONG IMPLEMENTATION SIGNAL / unchanged**

### H9 — Explicit Agent-runtime termination becomes a first-class control primitive

**STRONGLY STRENGTHENED**

Product-local stop controls are now complemented by open-protocol task lifecycle semantics

### H10 — Termination and remediation become separate lifecycle phases

**STRONGLY STRENGTHENED**

A terminal task can remain a stable historical boundary while different execution objects perform reconciliation

### H11 — Recovery requires a new execution identity boundary

**NEW / STRONG OPEN-PROTOCOL STRUCTURAL SIGNAL**

A2A says terminal tasks cannot be restarted while one context may compose multiple related tasks and messages

MCP 2026-07-28 formalizes Tasks as an extension family for long-running work; its current extension model gives asynchronous work stable task identity and cooperative cancellation

**Falsifier:** mature interoperable Agent systems consistently recover terminal tasks by transparently reactivating the same execution object with unchanged authority and no new auditable execution identity

## 6｜Friday Evidence / 28 August

### A2A — terminal task versus continuing context

A2A models work as stateful tasks carrying task ID, context ID, status, artifacts and history

Terminal states include completed, failed, canceled and rejected

A terminal task cannot be restarted

A `contextId` can still group multiple related tasks and messages

This gives W35 an explicit execution-identity boundary:

```text
old task = historical execution record
new task = new attempt / recovery execution
context = continuity across related work
```

### MCP 2026-07-28 — durable task identity

The final 2026-07-28 MCP release moves Tasks into the formal extension framework

The current Tasks extension models long-running work through server-generated task IDs plus `tasks/get`, `tasks/update` and `tasks/cancel`

Detailed cancellation semantics remain cooperative rather than transactional

This reinforces:

```text
cancellation intent
≠ proven physical termination
≠ rollback
```

TERMINAL TASK
