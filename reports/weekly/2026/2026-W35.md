## 0｜Saturday Judgment / 周六判断

W35 began by asking whether a trust change can alter something already active

Six days now expose a nearly complete runtime-recovery chain:

```text
24 Aug  continuous runtime trust
25 Aug  trust change → relying-resource denial
26 Aug  explicit Agent runtime stop
27 Aug  stop → residual-state reconciliation
28 Aug  terminal task → new recovery-task identity
29 Aug  recovery task → request-level authentication / authorization
```

The Saturday model is:

```text
TRUST / INCIDENT SIGNAL
→ RESOURCE DENIAL
→ CANCEL / STOP
→ TERMINAL TASK + RESIDUAL STATE
→ REMEDIATION
→ NEW RECOVERY TASK
→ AUTHENTICATE REQUEST
→ AUTHORIZE REQUEST / ACTION
→ CONTINUE RELATED CONTEXT
→ FOLLOW-UP VALIDATION
```

The key refinement is:

> **Context can remain continuous while authority is independently re-evaluated**

### H11 — Recovery requires a new execution identity boundary
**STRONGLY STRENGTHENED / REFINED**

Friday established that A2A terminal Tasks do not restart and that new related work can continue under the same `contextId`

Saturday adds the security boundary:

- the A2A server authenticates every incoming request
- requests are authorized according to authenticated identity and server policy
- task-resource operations remain authorization-scoped
- `TASK_STATE_AUTH_REQUIRED` can surface missing in-task authority
- the `AUTH_REQUIRED` transition itself must not be treated as proof that subsequent operations are authorized

The refined H11 is:

> **Recovery creates a distinct successor execution whose requests remain independently authorized even when context is preserved**

**Falsifier:** mature interoperable recovery safely permits successor Tasks to inherit authorization implicitly from shared context without request-level authorization checks

## 3｜Saturday Evidence / 29 August

### A2A request security

A2A requires incoming requests to be authenticated and leaves authorization decisions to the server's policy over authenticated identity

Task operations must be scoped to the authenticated caller's authorization boundaries

This prevents `contextId` from acting as an ambient permission token

### A2A in-task authorization

`TASK_STATE_AUTH_REQUIRED` allows a Task to pause for additional authorization rather than treating authority as permanent after task creation

The specification also prevents an important overclaim: transition into `AUTH_REQUIRED` is not itself authorization evidence for subsequent operations

This supports:

```text
Task exists
≠ Task currently has authority for every next action

AUTH_REQUIRED state
≠ authorization proof
```

### Saturday refinement

```text
NEW RECOVERY TASK
→ RELATED CONTEXT
→ NEW REQUEST
→ AUTHENTICATE
→ AUTHORIZE
→ EXECUTE
```

**Boundary:** fresh authorization decision ≠ fresh credential ≠ fresh human approval

## 5｜Corrections and Counterevidence / 更正与反证

No counterevidence was found against the A2A request-level authentication / authorization boundary

The evidence does constrain the claim:

- A2A does not define one universal authorization policy
- `AUTH_REQUIRED` does not itself authorize any action
- fresh authorization does not necessarily require a fresh credential
- fresh authorization does not necessarily require fresh human approval
- A2A request authorization does not prove all downstream external side effects are separately authorized

These constraints are retained as part of H11 rather than hidden

## 6｜Models, Infrastructure, Agents, and Governance / 模型、基础设施、智能体与治理

The emerging architecture separates the execution and security planes:

```text
EXECUTION
original task
→ terminal state
→ successor task
→ context continuity

SECURITY
request identity
→ authentication
→ authorization decision
→ permitted operation
```

MCP Tasks contributes long-running task identity and cooperative cancellation semantics

A2A contributes task/context semantics plus explicit request-security boundaries

GitHub / Foundry / OpenAI product mechanisms contribute real stop, retained-state and remediation examples

These layers are structurally complementary, not a single portable incident-recovery protocol

## 7｜Open Gaps / 未解决缺口

1. Can a recovery task explicitly reference the task it repairs or supersedes?
2. Can one incident ID span A2A task IDs, MCP task IDs and vendor-local session IDs?
3. Do successor tasks carry explicit delegated-user / sponsor evidence?
4. Can compensation itself be represented as a first-class task?
5. Can terminal tasks preserve a complete list of committed external effects?
6. Can non-code outputs expose withdraw / supersede / compensate state transitions?
7. Can recovery completion be independently evaluated?
8. Can exception / break-glass authority carry owner, reason, scope and expiry across systems?
