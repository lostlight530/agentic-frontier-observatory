## 1｜Executive Weekly Judgment / 周度核心判断
Task/execution and authorization surfaces continue to mature faster than successor authority, durable-effects rollback/remediation and recovery-completion contracts.

A2A directly establishes that authorization-required state is not itself authorization and does not automatically authorize later messages. MCP independently requires authentication/authorization checks on every task-related request, requires durable task creation before returning a task handle, and specifies cancellation as cooperative/eventually consistent rather than guaranteed stop. Together these sharpen the boundary without closing a recovery hypothesis.

## 2｜Current Evidence / 当前证据
- A2A retains `contextId`, task IDs and `referenceTaskIds`; generic task references are not typed recovery lineage.
- A2A `TASK_STATE_AUTH_REQUIRED` is not itself authorization; scope/validity/revocation remain implementation/issuer/extension-defined.
- MCP `SEP-2663` remains `Final` / Extensions Track; Tasks is still an extension intended to incubate before future core promotion.
- MCP task creation is durably resolvable before acknowledgement.
- MCP requires authentication and authorization checks on each task-related request.
- MCP `tasks/cancel` acknowledges cancellation intent; cancellation is cooperative/eventually consistent and does not guarantee actual stop or terminal `cancelled` state.
- NIST NCCoE Software and AI Agent Identity and Authorization remains `Reviewing Comments`.
- `F.748.93` remains Approved 2026-08-29 / `In force (prepublished)`; implementation/conformance unverified.

## 3｜Opening Hypotheses / 开启假设
### H38-1 — A normative task protocol adds typed recovery lineage — **OPEN**
**Strengthening evidence:** typed predecessor/supersedes/repairs/compensates or equivalent recovery relations.
**Current evidence:** neither checked A2A nor MCP Tasks provides such portable typed recovery lineage.

### H38-2 — Task continuation gains explicit successor or re-authorization semantics — **OPEN**
**Strengthening evidence:** delegation inheritance, explicit re-authorization, or scoped successor authority.
**Current evidence:** A2A denies automatic authority continuity; MCP per-request authz does not define successor authority.

### H38-3 — Durable effects gain portable rollback/compensation obligations — **OPEN**
**Strengthening evidence:** committed-effect evidence, retained-state obligations and rollback/compensation semantics together.
**Independent boundary evidence 2026-09-17:** MCP requires durable task creation, but `tasks/cancel` is only cooperative intent and does not guarantee runtime stop. Durable task state therefore does not establish committed-effect accounting, rollback or compensation.

### H38-4 — Continuous authorization and exception lifecycle become explicit — **OPEN**
**Strengthening evidence:** post-admission continuous authorization plus scoped exception/break-glass grant, expiry, revocation and reconciliation.
**Current evidence:** A2A leaves authorization scope/validity/revocation outside core state semantics; independently, MCP requires authn/authz on each task-related request. This strengthens evidence for repeated authorization checks but still does not establish a portable exception/recovery lifecycle.

### H38-5 — Recovery completion becomes portable proof — **OPEN**
**Strengthening evidence:** machine-readable proof that remediation/recovery obligations were completed and accepted by required authority.
**Current evidence:** no checked source closes this requirement.

## 4｜Durable Baseline / 稳定基线
`Capability != Deployability`; `Discovery != Authorization != Invocation`; `Identity != Credential != Authority`; `Authenticated Origin != Delegated User Authority`; `Transport Interoperability != Trust Interoperability`; `Protocol Publication != Operational Maturity`; `Admission != Continuous Authorization`; `Resource Denial != Runtime Stop`; `Runtime Stop != Rollback`; `Termination != Remediation`; `Context Continuity != Authority Continuity`; `referenceTaskIds != typed recovery lineage`; `Task reference != Task authority`.

Four-layer model: `SECURITY != EXECUTION != DURABLE EFFECTS != RECOVERY`.
